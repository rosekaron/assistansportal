## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client JWT → /api/profile PUT | Guardian-authenticated body writes to profile row (single-tenant) |
| client JWT → /api/assistants/:id PUT | Guardian-authenticated body writes to an assistants row |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-02-01 | Tampering | Explicit `.set({...})` whitelist — if a developer later replaces it with `.set(data)`, attacker could write arbitrary columns (e.g. `authId`, `createdAt`) | mitigate | Preserved in Task 1 + 2 action text and acceptance criteria. Code review enforces: any future edit that replaces the whitelist pattern must add new fields by NAME, not pass `data` as-is. |
| T-07-02-02 | Information Disclosure | pno (personnummer), IBAN, bank_account now writeable by whitelist | accept | Write path is guardian-only (`requireAuth + requireGuardian`). Single-tenant deployment. GDPR legal basis = employment relationship. Server never logs bodies (confirmed: `console.error("[assistant] error:", e)` logs exception only). |
| T-07-02-03 | Spoofing | `taxScheme` accepts only enum values at DB level (Postgres enum constraint). Unknown values rejected at DB with `invalid input value for enum tax_scheme`. | mitigate | Postgres enum is the enforcement boundary. Task 1 (Plan 01) created the enum constraint; this plan relies on it. Bad UI input surfaces as a 500 (acceptable per D-18 — strict validators ship in v1.2). |
| T-07-02-04 | Tampering | `skattetabell` accepts any integer — schema allows null, no range check (should be 29–40). Bad value reaches DB unchecked (D-18 accepts this) | accept for Phase 7 | D-18 explicitly defers range validation to v1.2 Submission Readiness Gate. Filing flow (FK/SKV PDF) will reject bad values at render time. |
| T-07-02-05 | Information Disclosure | GET /api/profile and GET /api/assistants return `SELECT *` (full row, including new sensitive columns) | accept | Consistent with existing pre-Phase-7 behavior. Both routes are `requireAuth + requireGuardian`. Single-tenant, only one guardian account can authenticate. Any tightening (field-level ACL) would be a broader refactor outside Phase 7 scope. |
| T-07-02-06 | Repudiation | No audit log of who changed which field; updatedAt only records last-write timestamp | accept | Outside Phase 7 scope. Future milestone could add an audit table. For now, single-user workflow makes repudiation non-issue. |
</threat_model>
