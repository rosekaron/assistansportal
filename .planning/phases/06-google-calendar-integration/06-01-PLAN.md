<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Google OAuth | Guardian's browser navigates to Google. Code parameter returned in callback URL is untrusted until exchanged server-side. |
| Google OAuth callback → /api/gcal/callback | `code` query parameter arrives from Google redirect. Server exchanges it via googleapis SDK against Google's token endpoint. |
| Server → settings table | OAuth tokens (access_token, refresh_token) written to PostgreSQL settings table in plaintext. Server has exclusive read/write. |
| Client → /api/gcal/calendars | Client reads calendar list from server. Endpoint is behind requireAuth + requireGuardian — assistant role cannot access. |
| CLIENT_URL env var → redirect target | Backend reads CLIENT_URL to build the post-OAuth redirect destination. This is a server env var, not user input. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing | /api/gcal/callback — `code` parameter | mitigate | googleapis `oauth2Client.getToken(code)` validates the code with Google's token endpoint server-to-server; an attacker-supplied code is rejected by Google. No additional validation needed. |
| T-06-02 | Tampering | /api/gcal/callback — `CLIENT_URL` redirect target | accept | `CLIENT_URL` is a server-controlled env var, not user input. The redirect target cannot be manipulated by a caller. Acceptable for single-tenant MVP. |
| T-06-03 | Information Disclosure | settings table — access_token, refresh_token stored plaintext | accept | Single-tenant PostgreSQL accessible only via server-side JWT-authenticated requests. Tokens never sent to client over any endpoint. Acceptable for MVP; document as v2 encryption candidate. |
| T-06-04 | Information Disclosure | /api/gcal/status returns gcal.email | accept | Email is the Google account email the guardian themselves connected. No third-party PII exposed. Endpoint is behind requireAuth + requireGuardian. |
| T-06-05 | Elevation of Privilege | /api/gcal/calendars, /api/gcal/connect | mitigate | `requireGuardian` middleware applied to all gcal routes (already in gcal.ts for /status and /disconnect; Task 1 adds it to /calendars). Assistant role cannot access any gcal endpoint. |
| T-06-06 | Denial of Service | /api/gcal/calendars — repeated calls exhaust Google API quota | accept | Default Google Calendar API quota (1,000,000 units/day) is not at risk for a single-guardian installation. React Query caches the response; the query re-fetches only on cache invalidation. |
| T-06-07 | Repudiation | gcal_access_token auto-refresh writes to settings table with no audit log | accept | Token refresh is an automated server-side operation, not a user action. No audit trail required for token maintenance. User-visible event (connect/disconnect) is detectable from gcal_connected flag. |
| T-06-08 | Spoofing | CSRF on GET /api/gcal/connect (initiates OAuth) | accept | GET /connect only redirects to Google; it has no state-changing effect until the callback completes. The callback requires a valid code from Google. SameSite cookie policy (already set by auth middleware from Phase 1) prevents forced redirects from third-party pages. |
</threat_model>
