## Tasks

### Task 1 — BUG-005: Add "Register yourself as assistant" UI to Assistants.tsx

**Goal:** Guardian who is also a personal assistant can register themselves — no invite flow, no email, immediate activation.

**What exists:**
- `POST /api/assistants/register-self` on server (checks for duplicate, creates assistant row, links auth account, creates active guardian link)
- `assistantsApi.registerSelf(data)` in `client/src/lib/api.ts`

**What's missing:**
- Any UI in `Assistants.tsx` to call `registerSelf`

**Implementation:**

1. Add state to `Assistants.tsx`:
   ```tsx
   const [selfOpen, setSelfOpen] = useState(false);
   const [selfForm, setSelfForm] = useState({ name: "", pno: "", phone: "", minWeeklyHours: "", isFlexible: false });
   ```

2. Add `registerSelf` mutation:
   ```tsx
   const registerSelf = useMutation({
     mutationFn: (data: Record<string, unknown>) => assistantsApi.registerSelf(data),
     onSuccess: () => {
       qc.invalidateQueries({ queryKey: ["assistants"] });
       setSelfOpen(false);
       setSelfForm({ name: "", pno: "", phone: "", minWeeklyHours: "", isFlexible: false });
     },
   });
   ```

3. Add "Register yourself" button next to the existing "Add assistant" / invite button. Label: **"I'm also an assistant"** — keep it human.

4. Add `<Dialog>` for the self-registration form:
   - Fields: Full name (pre-fill from profile.name if available), Personal ID (pno), Phone, Min weekly hours, Flexible checkbox
   - Submit calls `registerSelf.mutate({ name, pno, phone, minWeeklyHours: +minWeeklyHours, isFlexible })`
   - On success: dialog closes, assistant list refreshes

5. Hide the button if the guardian already has a linked assistant (detect via `assistants.some(a => a.authId === profile?.id)` — or rely on server 409).

**Test:** Guardian clicks "I'm also an assistant", fills name, submits → appears in assistant list, can clock in.

### Task 2 — BUG-002: Add week navigator to Home schedule grid

**Goal:** Guardian can navigate backward and forward through weeks on the Home schedule grid.

**Current state:**
- `Home.tsx:80`: `const weekDates = getWeekDates(0);` — hardcoded offset 0 (always current week)
- `getWeekDates` in `client/src/lib/utils.ts` — check signature; likely `getWeekDates(offsetWeeks: number)`

**Implementation:**

1. Add weekOffset state above `weekDates`:
   ```tsx
   const [weekOffset, setWeekOffset] = useState(0);
   const weekDates = getWeekDates(weekOffset);
   ```

2. Add navigation buttons to the schedule section header. Pattern: `← Previous week` | current week label | `Next week →`.

   Week label: use the first and last day of the week:
   ```tsx
   const weekLabel = `${weekDates[0]} – ${weekDates[6]}`;
   ```
   Or format to human-readable: `7–13 Apr` using `Intl.DateTimeFormat`.

3. Limit past navigation to 12 weeks (3 months back). No future limit needed.
   ```tsx
   <Button variant="ghost" size="sm" onClick={() => setWeekOffset(o => Math.max(o - 1, -12))} disabled={weekOffset <= -12}>
     ← Prev
   </Button>
   <Button variant="ghost" size="sm" onClick={() => setWeekOffset(o => o + 1)}>
     Next →
   </Button>
   ```

4. The `gcalEvents` query already keys on `weekDates[0]` — it will automatically re-fetch for the new week when weekOffset changes.

5. The `entries` query is unfiltered (fetches all) — the existing weekly filter in the grid already uses `weekDates`. No server change needed.

**Test:** Guardian clicks `← Prev` → grid shows previous week's dates and data. Clicks `Next →` → returns to current week.

### Task 3 — BUG-004: Verify invite email works end-to-end

**Goal:** Confirm the invite email flow actually delivers an email — code is wired, env vars present.

**Current state:**
- `misc.ts` POST `/invites` calls `sendAssistantInviteEmail` after inserting the row
- `email.ts` transporter configured with `GMAIL_USER` + `GMAIL_APP_PASSWORD`
- `server/.env` has both credentials set

**Verification steps (human checkpoint):**
1. Go to Assistants → invite a new assistant using a real email address you can check
2. Submit the invite form
3. Check the inbox — expect subject: `You've been invited to assist [patient] — Assistansportal`
4. Confirm the "Accept invitation →" link points to `/accept-invite?token=<invite-id>`
5. Check server logs for any `[invite] email failed:` errors

**If email fails (SMTP auth error):**
- Gmail App Password must be a 16-char app-specific password (not the Gmail login password)
- GMAIL_USER must match the account that generated the app password
- Verify at: https://myaccount.google.com/apppasswords

**Code fix (only if SMTP is confirmed working but email body has issues):**
- The `sendAssistantInviteEmail` function in `email.ts` is complete — no changes anticipated
- If the invite token isn't the right value, check `row.id` is the crypto newId (confirmed in misc.ts:72)

**Update UAT-BUG-LOG.md** after verification — mark BUG-004 Fixed or document the specific failure.
