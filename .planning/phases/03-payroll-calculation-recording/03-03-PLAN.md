**POST /api/payroll/generate** (place BEFORE /:id routes to avoid Express path conflict)
- requireAuth, requireGuardian
- Parse body: `MonthSchema.safeParse(req.body)` — 400 on failure
- Read env vars: `const hourlyRate = parseFloat(process.env.FK_HOURLY_RATE ?? "334")` and `const taxRate = parseFloat(process.env.EMPLOYER_TAX_RATE ?? "0.3142")`
- Fetch all assistants: `const allAssistants = await db.select().from(assistants)`
- Build month date range:
  ```typescript
  const { month } = parsed.data;
  const [yearStr, monStr] = month.split("-");
  const monthStart = `${month}-01`;
  const daysInMonth = new Date(parseInt(yearStr), parseInt(monStr), 0).getDate();
  const monthEnd = `${month}-${String(daysInMonth).padStart(2, "0")}`;
  ```
- For each assistant in `allAssistants`:
  1. Check for existing record: `const existing = await db.select().from(payrollRecords).where(and(eq(payrollRecords.assistantId, asst.id), eq(payrollRecords.month, month)))` — if `existing.length > 0`, push `existing[0]` to result array and `continue`
  2. Fetch approved entries for this assistant in the month: `db.select().from(entries).where(and(eq(entries.assistantId, asst.id), gte(entries.date, monthStart), lte(entries.date, monthEnd), eq(entries.reqStatus, "approved")))`
  3. Fetch absences overlapping the month: `db.select().from(absences).where(and(gte(absences.endDate, monthStart), lte(absences.startDate, monthEnd)))` then filter in-memory: `monthAbsences = rawAbsences.filter(a => a.assistantId === asst.id || a.assistantId === null)`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/payroll | Unauthenticated or assistant-role callers must be rejected; rate values must come from server env, not client body |
| client → /api/payments | DELETE must verify payment exists before removal; POST must verify payrollRecord exists before insert |
| generate body → DB | month string from client body drives DB query; must be validated to YYYY-MM format before use |
| approve state machine | Approved records must not be re-approved; status transition is one-way draft→approved |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Spoofing | All /api/payroll and /api/payments endpoints | mitigate | requireAuth validates JWT on every request; missing token returns 401 (tested by Wave 0 stubs) |
| T-03-02 | Elevation of Privilege | All /api/payroll and /api/payments endpoints | mitigate | requireGuardian rejects assistant-role JWT with 403; tested by Wave 0 stubs |
| T-03-03 | Tampering | POST /api/payroll/generate body — month parameter | mitigate | Zod validates `month` against `/^\d{4}-\d{2}$/` before any DB operation; invalid input returns 400 before reaching DB |
| T-03-04 | Tampering | POST /api/payroll/:id/approve — re-approval of locked record | mitigate | Route checks `record.status === "approved"` before transition; returns 409 if already approved (per D-13) |
| T-03-05 | Tampering | POST /api/payroll/generate — rate manipulation | mitigate | hourlyRate and taxRate are read exclusively from `process.env` (server-side); no client-supplied rate field accepted; values snapshotted into DB at generation time (D-02) |
| T-03-06 | Information Disclosure | GET /api/payroll returns all records | accept | Single-tenant deployment per D-03; only one guardian user per deployment; no cross-guardian data risk in v1 |
| T-03-07 | Tampering | POST /api/payments — orphaned payment insert | mitigate | Route verifies payrollRecord existence before insert; returns 404 if payrollRecordId is unknown |
| T-03-08 | Denial of Service | POST /api/payroll/generate called twice for same month | mitigate | Route checks for existing `payroll_records` row per `(assistantId, month)` before INSERT; if row exists, returns existing row without error (idempotent) |
| T-03-09 | Repudiation | No audit trail on payroll approval | accept | D-13 explicitly defers audit log to Phase 4; `approvedAt` timestamp provides minimum traceability; status lock (draft→approved) is one-way |
</threat_model>
