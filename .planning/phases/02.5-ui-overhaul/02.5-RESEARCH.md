## Summary

Phase 2.5 has two distinct sub-problems. The first is a hard technical bug: Tailwind CSS v3 JIT
is generating only base rules (51 total) with zero utility classes, rendering the app completely
unstyled. The second is a design system uplift from the current rough draft to a professional
B2B-grade healthcare aesthetic.

The Tailwind bug has a confirmed root cause discovered during this research: `client/package.json`
declares `"type": "module"`, making the entire `client/` directory an ESM module context. The
`tailwind.config.js` file uses `require('tailwindcss-animate')` — a synchronous CJS `require()`
call that is illegal in an ESM module. When Tailwind v3's PostCSS plugin attempts to load this
config, it receives either an error or an empty module, silently falling back to a bare default
config with no content paths defined. With no content paths, JIT generates only base resets —
exactly the 51-rule symptom reported. The `postcss.config.js` file also uses legacy object syntax
(`plugins: { tailwindcss: {}, autoprefixer: {} }`) which Vite ignores in favour of the inline
`vite.config.ts` PostCSS config; this is expected behaviour and is NOT the bug.

The design system uplift requires updating the CSS custom property token values in `index.css`
(after visual confirmation post-fix), applying them consistently across Layout.tsx,
AssistantDashboard.tsx, Dashboard.tsx, Leave.tsx, and the component library. No new libraries
are needed — the existing Radix UI + CVA + Tailwind stack is the correct foundation.

**Primary recommendation:** Fix the ESM/CJS require() conflict in tailwind.config.js first.
Replace `require('tailwindcss-animate')` with an ES import, confirm full utility output, then
execute the visual redesign.

### Pattern 1: ESM-Safe Tailwind Plugin Import

**What:** In an ESM module context (`"type": "module"` in package.json), `require()` is
forbidden. Tailwind plugins must be imported using ES module `import` syntax.

**When to use:** Mandatory when `client/package.json` has `"type": "module"`.

**Fix:**
```js
// tailwind.config.js — BEFORE (broken in ESM context)
plugins: [require("tailwindcss-animate")],

// tailwind.config.js — AFTER (ESM-safe)
import tailwindAnimate from "tailwindcss-animate";
// ...
plugins: [tailwindAnimate],
```

The file already uses `export default` at the top — adding `import tailwindAnimate` at the top
completes the conversion to full ESM syntax. [VERIFIED: tailwindcss-animate 1.0.7 has a CJS
main entry but can be imported via ES `import` statement because Node/bundlers handle the
interop automatically for CommonJS packages.]

### Pattern 2: Content Path Resolution

**What:** Tailwind JIT `content` paths are resolved relative to the config file location, not
the process CWD.

**Current config:**
```js
content: ["./index.html", "./src/**/*.{ts,tsx}"]
```

**Assessment:** With `tailwind.config.js` located at `client/tailwind.config.js` and
`index.html` at `client/index.html`, the relative paths `./index.html` and `./src/**/*.{ts,tsx}`
are correct. [VERIFIED: both `client/index.html` and `client/src/` exist.] Content paths are
NOT the root cause of the bug — the ESM/CJS conflict is.

When the config is loaded successfully after the fix, JIT will scan these paths and generate
all utility classes used in `.tsx` files.

### Pattern 3: Vite Inline PostCSS vs File-Based Config Precedence

**What:** When `vite.config.ts` defines `css.postcss` inline, Vite uses that and does NOT read
`postcss.config.js`. This is Vite's documented behaviour. [VERIFIED: vite.config.ts has inline
`css.postcss` config.]

**Implication:** `postcss.config.js` (`{ tailwindcss: {}, autoprefixer: {} }`) is dead code and
can be removed to eliminate confusion. It has no runtime effect.

**Assessment:** This is NOT a conflict — it is expected Vite precedence. The inline config
correctly passes `tailwindcss({ config: path.resolve(__dirname, './tailwind.config.js') })`.

### Pattern 4: CSS Variable Token + Tailwind Theme Extension

**What:** Tokens are defined as HSL triplets in `:root` in `index.css`, referenced as
`hsl(var(--token))` in `tailwind.config.js`. This is the standard shadcn/Radix pattern.

**Current token inventory:**
```
--background, --foreground
--card, --card-foreground
--popover, --popover-foreground
--primary, --primary-foreground
--secondary, --secondary-foreground
--muted, --muted-foreground
--accent, --accent-foreground
--destructive, --destructive-foreground
--border, --input, --ring
--radius
```

**Design update process:** Change HSL values in `index.css :root` only. All components that
use `bg-primary`, `text-muted-foreground`, etc. inherit the new values automatically. No
component-level color edits are needed for a palette change.

### Anti-Patterns to Avoid

- **Hard-coded color strings in component files:** The code already uses colour token classes
  (`bg-primary`, `text-muted-foreground`) correctly. Several places use Tailwind's built-in
  palette directly (`bg-blue-50`, `text-amber-600`, `bg-emerald-500`) for status states — this
  is acceptable for semantic colours that don't belong in the design token system.
- **Fixing postcss.config.js instead of tailwind.config.js:** The file-based PostCSS config is
  irrelevant (Vite ignores it). The bug lives entirely in `tailwind.config.js`.
- **Migrating to Tailwind v4 as the fix:** v4 uses a completely different config format (CSS-
  based, no `tailwind.config.js`). That is a separate migration, not a bug fix.

## Common Pitfalls

### Pitfall 1: Fixing the Wrong Config File

**What goes wrong:** Developer edits `postcss.config.js` to add explicit config path or remove
the Tailwind plugin, expecting it to change behaviour.

**Why it happens:** Two config files exist; the file-based one looks authoritative.

**How to avoid:** Vite's inline `css.postcss` config in `vite.config.ts` always takes
precedence. `postcss.config.js` is completely bypassed. All PostCSS changes must go through
`vite.config.ts` or the bug must be fixed in `tailwind.config.js` itself.

**Warning signs:** Editing `postcss.config.js` and seeing no change in the build.

### Pitfall 2: ESM/CJS Config Loading Silently Fails

**What goes wrong:** When Tailwind fails to load `tailwind.config.js` due to the `require()`
call in an ESM context, it does not throw a loud build error. It silently uses an empty default
config with no `content` paths defined. JIT produces only the base reset layer (51 rules).

**Why it happens:** Vite's PostCSS pipeline catches the config loading error gracefully. The
build succeeds but produces incomplete CSS.

**How to avoid:** After applying the fix, verify utility class count jumps from 51 to thousands
of rules. Check `document.styleSheets[0].cssRules.length` in the browser console; it should
exceed 5,000 for a project this size.

**Warning signs:** Build completes without errors, but `.flex`, `.bg-primary`, `.text-sm` are
absent from the stylesheet.

### Pitfall 3: Content Path Glob Not Matching `.tsx` Extensions

**What goes wrong:** Glob `./src/**/*.{ts,tsx}` doesn't match files if the working directory
at Tailwind scan time is different from `client/`.

**Why it happens:** Rarely relevant when using the explicit config path
`path.resolve(__dirname, './tailwind.config.js')` in `vite.config.ts`, since `__dirname` is
the directory of `vite.config.ts` (i.e. `client/`).

**How to avoid:** The fix from Pitfall 2 will also resolve this implicitly — once the config
loads correctly, content paths resolve from `client/` correctly.

**Warning signs:** Config loads (no ESM error) but utility count is still low.

### Pitfall 4: Design Token Changes Affecting Both Themes Simultaneously

**What goes wrong:** Changing `--primary` value breaks components that used the OLD primary
colour for non-semantic purposes (e.g., a hardcoded `bg-blue-500` progress bar that was added
as a workaround).

**Why it happens:** Some components bypass the token system for specific states (Dashboard.tsx
line 198: `bg-blue-500` for the fill bar).

**How to avoid:** After token update, visually inspect Dashboard, AssistantDashboard, Leave,
Layout. Pay attention to status colours (amber, emerald, red) which are intentionally hardcoded
to Tailwind's built-in palette and should not be changed.

### Pitfall 5: Typography Scale Override Breaks Radix Primitives

**What goes wrong:** Overriding `font-size` globally (e.g., in `@layer base`) causes Radix
portal content (dialogs, select dropdowns) to render with wrong sizes.

**Why it happens:** Radix portals render at `document.body` level where global styles apply.

**How to avoid:** Typography changes should use the theme `fontSize` extension in
`tailwind.config.js` (already done correctly) rather than global CSS. The existing
`body { font-size: 16px; }` in `index.css` is correct.
